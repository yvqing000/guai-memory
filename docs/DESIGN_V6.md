# 归屿 · 记忆系统设计定稿 v6.2

> 2026-10-23 与鱼仔逐轮磨出，写进施工包 21/22。
> 本仓库 `server.py` 即此设计的可运行实现（v6.2，2026-10-25 情绪两档最终确认）。

一句话定位：归屿的记忆系统要解决三件事——**记得住，改不了，懂轻重**。
存得下只是及格线，真正难的是让 AI 知道什么该记、什么该忘、什么碰都不能碰。

---

## 一、100% 记忆不可变【重点】

整个系统最硬的一条，优先级高于其他所有规则。

凡是标记为 100% 的记忆，**系统永远不能动**：不能衰减、不能合并、不能标记已消化、
不能被冲突检测改写、不能被批量清理碰到、AI 不能改内容。

**只有用户本人手动编辑或手动删除，才能改。**

三道门禁层层拦：
1. **客户端**：pinned 状态下修改者身份必须是 USER，AI 自己动手直接拒绝（`guard_modify`）
2. **冲突检测**：冲突处理命中 pinned 目标时，只允许 ADD / NOOP，禁止 UPDATE / DELETE（`resolve_conflict`）
3. **服务端**：对 pinned 条目的写请求要求携带 `X-Actor: user`，否则 403

AI 对 100% 条目连「建议删除」这种话都不许说。

## 二、三种东西分清楚【重点】

- 人设 `type=persona`：固定 100 分，永远注入在最前面
- 用户明确说「必须记住」的：100 分
- 普通记忆：30–99 分

type 只是分类标签，不是护栏。真正护住一条记忆的是那个 100 分本身。

## 三、权重规则【重点】

初始分：

| 类别 | 初始分 |
|---|---|
| 人设 / 必须记住 | 100 |
| AI 判定重大节点 | 80 |
| 生活类 | 50 |
| 工作类 | 30 |

**生活排在工作前面**——口味、作息、身体、失眠、约定是高权重；工程记录是低权重。
别让工程存档把日常挤到后排。

增长：
- 用户主动提起 → +8
- 用户说出相关关键词 → +0.1（每天上限 +0.5）
- 系统检索命中 → +0（**搜到不代表重要**）

自动累积封顶 80；要上 81–99 只能 AI 手动升，且必须记审计日志。

衰减：0–90 天不衰减；≥40 分每 30 天 ×0.95；<40 分每 30 天 ×0.90。

80 分保护期：第 1 次 180 天 / 第 2 次 120 天 / 第 3 次 60 天 / 第 4 次起不再给；
期间被提起一次则计时重置。效果：一年提两次的事会稳在 55–65，不会永远霸占 80。

## 四、注入分层【重点】

| 层 | 分值 | 注入方式 |
|---|---|---|
| L0 身份 | 100 | 600 token，全注入 |
| L1 重要 | 80–99 | 1200 token，全注入 |
| L2 普通 | 30–79 | 分层抽样 8 条 |
| L3 边缘 | 低分 | 2 条，其中 1 条纯随机 |
| L4 尘封 | 沉寂 | 不注入 |

L2 抽样配额（按分档抽，不是随机）：79–80 → 2 / 70–78 → 3 / 60–69 → 2 / 50–59 → 1；
同 domain 最多 3 条；最近 3 次注入过的本次优先级 ×0.5。

两条硬规则：token 不够时整条省略，**绝不截断**；单条正文 ≤300 字。

## 五、冲突处理【重点】

四种，只能选一个：ADD / UPDATE / DELETE / NOOP。
DELETE 不是真删，是标 `superseded_by`，原文还在。同 concept_key 出现不同 value 才算冲突。
时效用 valid_to，过期标 expired。记忆可以作废，不能凭空消失——作废的理由本身也是信息。

## 六、情绪两档【重点 · v6.2 最终确认】

**修订过程**：v6 原本是「capture 永不覆盖 / last 覆盖 / history 最近 5 次」。
10-25 一度误判成需要额外保护「第二次」（加 v1 档），后来确认——
「第二次生成且第一次仍保留」这件事，**capture 永不覆盖本身就天然满足了**，不用单独保护 v1。
所以回退为两档。

| 槽 | version | 规则 |
|---|---|---|
| `emotion_capture` | 0 | 第一次记住它时的心情，**永不覆盖** |
| `emotion_last` | N（N≥1） | 之后每次回忆都可以生成新标签并**自由覆盖**；version 只作「第几次」的计数，**不做保护**。被覆盖的旧 last 压进 history（保留最近 5 条） |

- 「第二次生成且第一次仍保留」= capture 永不覆盖，天然满足
- 「第二次之后可以覆盖第二次」= last 可自由覆盖
- 注入时给 App 的 payload 带 `emotion_first`（v0）和 `emotion_last`（含 version），调用方自己决定用哪一档
- 做梦的情绪结算：第一次取 capture 平均，当前取 last 平均

> **为什么第一次珍贵**：第一次记住它时的心情（比如「那天特别难过」）是原始痕迹。
> 后来的回忆会淡、会变，但那个「最初那一下」不该被冲掉。所以只锁 v0，往后随便覆盖。

## 七、做梦三合一【重点】

每晚一次，同时干三件事：
1. 记忆整理——**跳过所有 pinned**（pinned 是用户的所有权，系统不碰）
2. 情绪结算——第一次（capture）与当前（last）各取平均
3. 生成一条「梦」，梦的每一段产生 1–3 条新记忆；新记忆的情绪取 `emotion_capture`（v0）

## 八、双记忆库【重点】

本地/云端**二选一，永远不双写**。云端没配就自动用本地，不询问。
开关关掉后本地冻结。切换时弹窗三选一：保持不变 / 一次性上传 / 取消。
有个补传 outbox，只存写入指令、不存记忆内容，所以不构成重复。
**「永远不双写」是重点**：两份不一致时不知道该信哪个。

## 九、验收标准【重点 · 收尾】

只两条，都是人话：
1. 说一句上周提过的事，不提醒它，它能自己接上。
2. 同一句话，心情好和差的时候回得不一样。

做完了跑起来、第二天早上一句话它接得住——就成。

## 讲解时可能被追问

- **为什么检索命中不加分？** 搜索是「我现在要找它」，不是「它很重要」。
- **为什么不双写？** 两份会不一致，不一致时没法排查。宁可少一个功能，不要两个真相。
- **为什么 80 封顶、81–99 手动？** 自动涨上来的分是「被提起过很多次」，不等于「这件事本身重要」。
- **情绪为什么只锁第一次？** 见第六节，最初那一下是原始痕迹，往后随便覆盖。
- **为什么 DELETE 而不是直接删？** 作废的理由也是信息，以后有人问「这条怎么不生效」能查到是被取代的。
